# Internationalization (i18n)

Proper provides full internationalization and localization support through YAML-based translations, CLDR-aware pluralization, and Babel integration for formatting dates, numbers, and currencies.

## Installation

Install the i18n blueprint with:

```bash
proper install i18n
```

This creates:

- `config/locales/` directory with an example `en.yml` file
- Adds `CurrentLocale` and `CurrentTimezone` concerns to `AppController`
- Installs `babel` and `poyo` as dependencies

After installation, your `AppController` will include the new concerns:

```python
from proper import Controller
from proper.concerns import CurrentLocale, CurrentTimezone, OriginProtection, RateLimiting
from .concerns.security_headers import SecurityHeaders


class AppController(
    Controller,
    OriginProtection,
    RateLimiting,
    SecurityHeaders,
    CurrentLocale,
    CurrentTimezone,
):
    pass
```

## Configuration

The i18n system is configured via `config/main.py`:

```python
# config/main.py
LOCALE_DEFAULT = "en"       # Fallback locale
TIMEZONE_DEFAULT = "UTC"    # Fallback timezone
```

`app.i18n` is always available, even before installing the `i18n` blueprint. Babel-backed formatters (dates, numbers, currencies, byte sizes — both as `app.i18n.*` methods and as Jinja filters) work out of the box using `LOCALE_DEFAULT` / `TIMEZONE_DEFAULT`.

The `config/locales/` directory is only required for *translations*. Without it, `app.i18n("some.key")` echoes the key back unchanged; with it, the YAML files are loaded and lookups resolve normally. The `proper install i18n` blueprint adds the directory plus the `CurrentLocale` / `CurrentTimezone` concerns so the resolved locale/timezone can vary per request and per user.


## Translation Files

Translations are stored as YAML files in the `config/locales/` directory. Both `.yml` and `.yaml` extensions are supported. Files in subdirectories are loaded recursively.

### Basic Structure

Each file is keyed by locale at the top level:

```yaml
# config/locales/en.yml
en:
  hello: "Hello world"
  greeting: "Hello {name}"
  site:
    title: "My Application"
    tagline: "Built with Proper"
```

```yaml
# config/locales/es.yml
es:
  hello: "Hola mundo"
  greeting: "Hola {name}"
  site:
    title: "Mi Aplicacion"
    tagline: "Hecho con Proper"
```

### Nested Keys

Nested YAML maps are accessed via dot notation:

```python
app.i18n("site.title")     # "My Application"
app.i18n("site.tagline")   # "Built with Proper"
```

### String Interpolation

Use named placeholders in curly braces. Pass the values as keyword arguments:

```yaml
en:
  greeting: "Hello {name}"
  welcome: "Welcome to {place}, {name}!"
```

```python
app.i18n("greeting", name="Alice")              # "Hello Alice"
app.i18n("welcome", name="Alice", place="Oz")   # "Welcome to Oz, Alice!"
```

### Pluralization

Pluralization follows the [CLDR plural rules](https://cldr.unicode.org/index/cldr-spec/plural-rules) for each locale. Define plural forms as a dictionary:

```yaml
en:
  apples:
    one: "{count} apple"
    other: "{count} apples"

  messages:
    zero: "No messages"
    one: "{count} message"
    other: "{count} messages"
```

```python
app.i18n("apples", count=1)     # "1 apple"
app.i18n("apples", count=5)     # "5 apples"
app.i18n("messages", count=0)   # "No messages"
```

The `count` keyword is automatically available for interpolation.

The lookup order for plural forms is:

1. Exact count as key (e.g., `0`, `1`, `42`)
2. `"zero"` key (when count is 0)
3. CLDR plural form for the locale (`"zero"`, `"one"`, `"two"`, `"few"`, `"many"`, `"other"`)

Languages like Arabic, Polish, or Russian have more plural forms than English. For example, Russian uses `"one"`, `"few"`, `"many"`, and `"other"`:

```yaml
ru:
  apples:
    one: "{count} яблоко"
    few: "{count} яблока"
    many: "{count} яблок"
    other: "{count} яблока"
```

### YAML Gotcha: Boolean Strings

YAML interprets these case-insensitive strings as booleans: `true`, `false`, `on`, `off`, `yes`, `no`. Quote them if you want them as strings:

```yaml
en:
  "yes": "yup"
  enabled: "ON"
```

### Territory-Specific Overrides

You can define territory-specific translations that override the base language. For example, `en_GB.yml` overrides specific keys from `en.yml` while falling back to the base language for everything else:

```yaml
# config/locales/en.yml
en:
  color: "color"
  greeting: "hello"
```

```yaml
# config/locales/en_GB.yml
en_GB:
  color: "colour"
```

```python
app.i18n("color", locale="en_GB")      # "colour" (overridden)
app.i18n("greeting", locale="en_GB")   # "hello" (falls back to en)
```

### Multiple Files per Locale

You can split translations across multiple files for organization. All files for the same locale are merged together:

```
config/locales/
├── en.yml              # General translations
├── en_models.yml       # Model-related translations
├── es.yml
└── admin/
    └── en.yml          # Admin-specific translations
```

Files in subdirectories are loaded recursively. When the same key appears in multiple files, the last one loaded wins.


## Using Translations

### In Python Code

The `app.i18n` object is callable. Calling it is a shortcut to `app.i18n.translate()`:

```python
app.i18n("hello")                         # "Hello world"
app.i18n("greeting", name="Alice")        # "Hello Alice"
app.i18n("apples", count=3)               # "3 apples"
app.i18n("hello", locale="es")            # "Hola mundo"
```

### In Templates

In Jinja templates, the `_()` function is a global alias for `app.i18n.translate()`:

```html+jinja
<h1>{{ _('hello') }}</h1>
<p>{{ _('greeting', name=user.name) }}</p>
<p>{{ _('apples', count=cart.item_count) }}</p>
```

### Missing Translations

If a key is not found, the translation returns `<missing:key_name/>`, which renders visibly in the page so you can spot untranslated content during development.

If i18n support is not installed (no locale files exist), the key itself is returned as-is.

### Lazy Translations

`app.i18n.lazy_translate` returns a wrapper whose `__repr__` calls the translator at render time. Use it where the locale is not yet resolved at evaluation time — typically class-level form field labels or other module-level constants:

```python
from proper import current

t = current.app.i18n.lazy_translate

class ContactForm(f.Form):
    name = f.TextField(label=t("contact.name"))
    email = f.EmailField(label=t("contact.email"))
```

Each `t(...)` call captures the key and arguments; the actual lookup against `current.locale` happens when the wrapper is converted to a string (e.g. during rendering).

Inside actions and templates, `app.i18n(...)` (or `_(...)` in Jinja) already resolves at the right moment — `lazy_translate` is only needed for values that need to outlive the current request scope.

### Locale Negotiation

`app.i18n.negotiate_locale(accepted)` picks the best match between a list of accepted locales (typically `request.accept_language`) and the locales that actually have translation files. Returns the matched locale or `None`.

It is used internally by the `CurrentLocale` concern, but you can call it directly if you need to make the same decision elsewhere — e.g. when generating links to localized pages, or in a custom locale picker.


## Locale Resolution

The `CurrentLocale` concern determines the locale for each request. It checks these sources in order:

1. **URL parameter** - `?locale=es`
2. **Cookie** - a `locale` cookie set by a previous request
3. **User attribute** - `current.user.locale` (if a user is logged in)
4. **Content negotiation** - best match from the `Accept-Language` header against available locales
5. **Default** - `LOCALE_DEFAULT` from config

The resolved locale is stored in `current.locale` and used automatically by all translation and formatting functions.

The concern also modifies the ETag to include the locale, so HTTP caches correctly vary responses by language.


## Timezone Resolution

The `CurrentTimezone` concern determines the timezone for each request, following the same pattern:

1. **URL parameter** - `?timezone=America/Lima`
2. **Cookie** - a `timezone` cookie
3. **User attribute** - `current.user.timezone` (if a user is logged in)
4. **Default** - `TIMEZONE_DEFAULT` from config

The resolved timezone is stored in `current.timezone` and used automatically by date/time formatting functions.


## Formatting with Babel

Proper integrates [Babel](https://babel.pocoo.org/) for locale-aware formatting of dates, times, numbers, and currencies. All formatting methods respect the current locale and timezone automatically.

### Date and Time Formatting

```python
from datetime import datetime, date, timedelta

# Format a datetime (uses current locale and timezone)
app.i18n.format_datetime(dt)                          # "Apr 1, 2007, 3:30:00 PM"
app.i18n.format_datetime(dt, format="full")           # "Sunday, April 1, 2007, 3:30:00 PM EDT"
app.i18n.format_datetime(dt, format="short")          # "4/1/07, 3:30 PM"

# Custom patterns
app.i18n.format_datetime(dt, "yyyy.MM.dd 'at' HH:mm")  # "2007.04.01 at 15:30"

# Force a specific locale or timezone
app.i18n.format_datetime(dt, locale="de_DE")           # "01.04.2007, 15:30:00"
app.i18n.format_datetime(dt, timezone="US/Eastern")    # Converts to Eastern time

# Format a date (no time component)
app.i18n.format_date(d)                                # "Apr 1, 2007"
app.i18n.format_date(d, format="full", locale="de_DE") # "Sonntag, 1. April 2007"

# Format a time
app.i18n.format_time(t)                                # "3:30:00 PM"

# Format a timedelta (relative time)
app.i18n.format_timedelta(timedelta(hours=3))          # "3 hours"
app.i18n.format_timedelta(timedelta(days=14))          # "2 weeks"
app.i18n.format_timedelta(
    timedelta(hours=-2),
    add_direction=True,
)                                                       # "2 hours ago"
```

### Number and Currency Formatting

```python
# Decimal numbers
app.i18n.format_decimal(1234567.89)                    # "1,234,567.89"
app.i18n.format_decimal(1234567.89, locale="de_DE")    # "1.234.567,89"

# Percentages
app.i18n.format_percent(0.75)                          # "75%"

# Currency
app.i18n.format_currency(99.99, "USD")                 # "$99.99"
app.i18n.format_currency(99.99, "EUR", locale="de_DE") # "99,99\u00a0€"

# Compact numbers
app.i18n.format_compact_decimal(1234567)               # "1M"
app.i18n.format_compact_currency(1234567, "USD")       # "$1M"

# Scientific notation
app.i18n.format_scientific(1234567)                    # "1.234567E6"
```

### File Size Formatting

`format_size` renders a byte count as a human-readable string with binary (1024) units. The number is localized through Babel, so the decimal separator follows the active locale.

```python
app.i18n.format_size(1024)                              # "1 KB"
app.i18n.format_size(15_678)                            # "15.3 KB"
app.i18n.format_size(1_073_741_824)                     # "1 GB"
app.i18n.format_size(133_235_678, precision=5)          # "127.06 MB"
app.i18n.format_size(133_235_678, precision=5, locale="de")  # "127,06 MB"
```

### List Formatting

```python
app.i18n.format_list(["Alice", "Bob", "Carol"])        # "Alice, Bob, and Carol"
app.i18n.format_list(["Alice", "Bob", "Carol"], locale="es")  # "Alice, Bob y Carol"
```

### Calendar Data

```python
# Get localized day names
app.i18n.get_day_names()                    # {0: 'Monday', 1: 'Tuesday', ...}
app.i18n.get_day_names(width="abbreviated") # {0: 'Mon', 1: 'Tue', ...}

# Get localized month names
app.i18n.get_month_names()                  # {1: 'January', 2: 'February', ...}

# Currency info
app.i18n.get_currency_name("USD")           # "US Dollar"
app.i18n.get_currency_symbol("USD")         # "$"
```

### In Templates

All formatting methods are available as Jinja filters. They are registered on every Proper app — you don't need to install the `i18n` blueprint to use them; without it they format against `LOCALE_DEFAULT` / `TIMEZONE_DEFAULT`.

```html+jinja
<!-- Date formatting -->
<time>{{ event.starts_at|format_datetime }}</time>
<time>{{ event.starts_at|format_date(format="full") }}</time>

<!-- Relative time -->
<span>{{ event.duration|format_timedelta }}</span>

<!-- Numbers and currency -->
<span>{{ product.price|format_currency("USD") }}</span>
<span>{{ stats.rate|format_percent }}</span>
<span>{{ stats.total|format_decimal }}</span>
<span>{{ stats.total|format_compact_decimal }}</span>

<!-- File sizes -->
<span>{{ attachment.byte_size|format_size }}</span>

<!-- Lists -->
<p>{{ attendees|format_list }}</p>
```

Available filters: `format_datetime`, `format_date`, `format_time`, `format_timedelta`, `format_skeleton`, `format_list`, `format_decimal`, `format_compact_decimal`, `format_currency`, `format_compact_currency`, `format_percent`, `format_scientific`, `format_size`.


## Format Options Reference

### Date/Time Formats

The `format` parameter accepts these presets or a custom pattern:

| Preset     | Example (en_US)                         |
|------------|-----------------------------------------|
| `"short"`  | 4/1/07, 3:30 PM                         |
| `"medium"` | Apr 1, 2007, 3:30:00 PM                 |
| `"long"`   | April 1, 2007, 3:30:00 PM EDT           |
| `"full"`   | Sunday, April 1, 2007, 3:30:00 PM EDT   |

Custom patterns use [Unicode date format symbols](https://www.unicode.org/reports/tr35/tr35-dates.html#Date_Field_Symbol_Table):

```python
app.i18n.format_datetime(dt, "yyyy-MM-dd HH:mm")    # "2007-04-01 15:30"
app.i18n.format_datetime(dt, "EEE, MMM d")           # "Sun, Apr 1"
```

### Calendar Data Widths

| Width          | Example (Monday)  |
|----------------|--------------------|
| `"wide"`       | Monday             |
| `"abbreviated"`| Mon                |
| `"short"`      | Mo                 |
| `"narrow"`     | M                  |


## Checking Locale Completeness

During development, you can check which locales are missing translations:

```python
missing = app.i18n.test_for_incomplete_locales("en", "es", "fr")
# {
#     "es": {"site.tagline", "advanced.feature"},
#     "fr": {"greeting", "site.tagline"},
# }
```

This compares all keys across the specified locales and returns which keys are missing from each. If no locales are specified, all available locales are tested.
